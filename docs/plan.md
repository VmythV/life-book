## 阶段 1：打通三端

目标：在本地，三端都能用同一个用户名登录，看到空的“今天”页面。

**共享包**

- [ ] `packages/core`：zod、基础类型（记录类型、日期和时刻格式）、Vitest
- [ ] `packages/api-client`：基于服务端路由类型的 HTTP 客户端、登录状态管理、TanStack Query 的 `QueryClient` 默认配置

**后台服务 `apps/server`**

- [ ] Hono 骨架、`/health`、用 zod 校验环境变量
- [ ] `docker-compose.yml` 启动 PostgreSQL 18；`.env.example`
- [ ] Drizzle 配置；首个迁移包含 `users`、`sessions`、`user_settings`
- [ ] 用户名 + 密码认证：注册、登录、退出、修改密码；scrypt 哈希；会话中间件把 `userId` 放入上下文；`GET /api/v1/me`
- [ ] 重置密码脚本 `reset-password <username>`（没有邮箱，忘记密码时在本地用）
- [ ] 集成测试基础：连接测试库，每个测试结束后清空数据
- [ ] 注册、登录、退出和访问 `/me` 的集成测试

**Web `apps/web`**

- [ ] Vite + React + TanStack Router + TanStack Query + Tailwind CSS，接入 `design-tokens`
- [ ] 注册和登录页面、需要登录的布局（左侧导航）、空的“今天”页面

**手机 `apps/mobile`**

- [ ] Expo Router；登录和注册页（令牌存 SecureStore）；开发时通过本机局域网地址访问服务端
- [ ] 底部标签“今天 / 生活簿 / 家中 / 我的”，先放空页面
- [ ] 在 iOS 模拟器和 Android 真机上跑通开发构建

**工程**

- [ ] 根脚本 `pnpm dev`：同时启动服务端和 Web
- [ ] CI 增加 PostgreSQL service，跑服务端集成测试

**完成标准**：在本地，同一个用户名在 Web、iOS 模拟器和 Android 真机上都能登录和退出；未登录访问 API 返回 401；CI 通过。

## 阶段 2：MVP

目标：重复日常、重要日期和备忘可以在三端使用，手机能按时收到提醒，自己每天在用。

**业务规则 `packages/core`**（先写测试）

- [ ] 重复规则展开：每天、每周（可多选星期）、每月（月末取当月最后一天）、每年（2 月 29 号平年取 28 号）、间隔 N、按日期或次数结束
- [ ] 周期实例状态：待完成、已完成、已跳过、逾期；逾期最多回看 30 天，同一事项合并显示
- [ ] 重要日期：下次发生日、还有几天、年龄或第 N 周年
- [ ] 提醒时刻计算（按用户时区）和 `reminderKey`
- [ ] 今天聚合与排序

**后台服务**

- [ ] `records` 增删改查：按类型分发，支持幂等 `id` 和 `version` 乐观锁
- [ ] 重复日常规则和周期实例（完成、跳过、撤销）
- [ ] 重要日期、备忘、提醒
- [ ] `GET /today`、`GET /reminders/upcoming`
- [ ] 列表筛选与 `ILIKE` 搜索、分类和标签（新建与选择）
- [ ] 用户隔离测试：每个接口都验证访问他人数据时返回 404

**Web**

- [ ] 今天页面：完成、跳过
- [ ] 生活簿：列表加详情双栏，按类型和分类筛选，搜索
- [ ] 三类记录的新建和编辑表单，包含提醒设置
- [ ] 设置页：时区、默认提醒时间、退出登录

**手机**

- [ ] 今天、生活簿、记录详情；“+”新建三类记录
- [ ] 完成和跳过；下拉刷新
- [ ] 在第一次设置提醒时申请通知权限；拒绝后说明影响和开启方法
- [ ] 通知调度：启动、回到前台和修改后拉取 `reminders/upcoming`，重新排最近 60 条
- [ ] 通知动作：“完成”（调用 API）、“稍后提醒”（本地重排）
- [ ] 查询缓存持久化，离线时只读并提示

**完成标准**：自己连续使用一周；提醒在 iOS 和 Android 上按时到达；在一端修改，另一端刷新后可以看到。

## 工作方式

- 在分支上开发，通过 PR 合并；CI（`pnpm verify`）通过才能合并。
- 提交信息用 Conventional Commits（如 `feat(server): add records api`），一个提交是一个完整的小改动。
- 业务规则先在 `core` 写单测，再写实现。
- 行为、表结构或接口变化时，同步更新 `docs/` 中对应的文档；重要取舍追加到 [决策记录](decisions.md)。
