# 生活有谱时间与重复规则

> 项目代号：`life-book` · 版本：v1.1 · 更新日期：2026-07-27 · 状态：文档基线
>
> 权威范围：日期时间语义、时区、自然日、重复算法、发生项计算和时间边界
>
> 不负责：系统通知调度状态、领域物理字段、页面布局和模型解析实现
>
> 依赖文档：[领域模型](domain-model.md)、[业务规则](business-rules.md)、[产品需求基线](product-features.md)、[术语表](glossary.md)

时间错误会直接造成错误提醒和历史破坏。本规范所有算法必须实现为使用显式时钟、IANA 时区和固定时区数据库版本的确定性逻辑，并用测试向量验证。

## 1. 时间值分类

### REC-001：禁止用一个时间戳表达所有场景

系统必须区分：

| 值 | 示例 | 保存语义 |
| --- | --- | --- |
| 全天日期 | 2026-10-20 的结婚纪念日 | 日历日期，不含时刻，不进行时区换算。 |
| 浮动本地时间 | 每天晚上 21:00 吃药 | 用户所在时区的钟表时间；旅行后仍为当地 21:00。 |
| 时区绑定时间 | 东京时间 2026-10-03 09:00 | 始终按指定 IANA 时区解释；其他地区只改变显示。 |
| 绝对时刻 | 线上直播的唯一开始时刻 | 时间轴上的同一瞬间；显示钟表时间随时区改变。 |

业务字段不得只保存 `Instant` 后推测原始本地日期，也不得只保存本地字符串后假设当前时区永不变化。

### REC-002：`ScheduleSpec`

逻辑时间结构必须能表达：

```text
ScheduleSpec
├── all_day
│   └── localDate
└── timed
    ├── timeBehavior: floating_local | zoned | instant
    ├── localDate/localTime（floating_local 或 zoned）
    ├── timeZoneId（zoned 必填；floating_local 解析时使用当前用户时区）
    ├── instant（instant 必填）
    └── disambiguation（遇到 DST 重叠时的选择）
```

`ScheduleSpec` 是逻辑结构；机器字段由 Schema 定义。重复事项的规则段只允许 `all_day`、`floating_local` 或 `zoned`，P0 不提供“每 24 小时绝对重复”。

### REC-003：精度

- P0 用户输入和提醒精度为分钟；秒固定为 0。
- `Instant` 存储精度至少到毫秒，用于稳定排序、冲突和日志。
- 比较业务到期使用分钟/自然日语义，不因存储毫秒差异产生重复实例。
- 显示不默认展示秒和毫秒。

## 2. 默认时间行为

### REC-010：按来源选择默认语义

| 场景 | 用户没有指定时区时的默认 | 原因 |
| --- | --- | --- |
| 重复事项计划时间 | `floating_local` | “每天/每周几点”通常跟随用户当地生活。 |
| 重要日期 | `all_day` | 生日、纪念日和到期日首先是日历日期。 |
| 清单仅日期截止 | `all_day` | 表示该日结束前完成。 |
| 清单日期+时间截止 | `floating_local` | 普通生活截止跟随当地钟表。 |
| 备忘指定提醒 | `floating_local` | 未声明时区时按用户当前生活时区理解。 |
| 智能输入明确说“东京时间”等 | `zoned` | 保留用户明确指定的地区时区。 |
| 导入明确绝对 UTC 时刻 | `instant` | 不丢失外部数据的绝对语义。 |

手动页面可以在高级选项显示时间行为。用户没有选择时，确认页不必展示技术名，但应在跨时区相关场景显示“按当地时间”或具体时区。

### REC-011：缺少时刻时的默认

产品不得用一个默认时刻改变全天业务日期：

- 全天重复事项在该自然日全天可处理，到下一日 00:00 才派生逾期；
- 仅日期清单在日期结束时到期，到下一日 00:00 才派生逾期；
- 重要日期在该自然日展示，不存在“到期小时”；
- 全天对象需要系统通知时，默认通知时刻为用户当地 09:00，并在确认页标记为系统建议；
- 用户设置中的默认全天提醒时刻可以改变未来新计划，不静默改写已有提醒。

### REC-012：模糊时段建议

智能输入只说时段而没有具体时间时，使用地区可配置的建议并在确认页标记：

| 中文时段 | P0 建议时间 |
| --- | --- |
| 早上 / 上午 | 09:00 |
| 中午 | 12:00 |
| 下午 | 15:00 |
| 晚上 | 20:00 |
| 睡前 / 夜里 | 必须追问；不使用统一建议 |

用户只说“明天提醒我”时可以建议明日 09:00，不必消耗唯一追问；“下周”“过几天”“晚点”等连日期都不唯一的表达必须追问。

## 3. 当前时间、地区和时区

### REC-020：当前上下文

每次时间计算显式接收：

- 当前 `Instant`；
- 当前用户 `TimeZoneId`；
- 地区语言；
- 周起始日；
- 时区数据库版本；
- 适用记录自己的时间行为和时区。

测试不得直接读取机器当前时间或默认时区。智能请求中的“当前日期”从同一上下文生成。

### REC-021：用户当前时区

- P0 默认跟随操作系统当前 IANA 时区。
- App 启动、回到前台或收到时区变化信号时更新 `AppPreferences` 并触发未来时间重算。
- 固定 UTC 偏移不是有效的长期时区；系统只能得到偏移而无法确定地区时，保留上次有效 IANA 时区并提示检查。
- 用户手动关闭系统自动时区不改变产品规则，仍以系统报告时区为准。

### REC-022：时区变化

| 时间行为 | 时区从 A 变到 B 后 |
| --- | --- |
| 全天日期 | 日期不转换，仍在同名日历日出现。 |
| 浮动本地时间 | 钟表日期和时间不变，使用 B 重新解析绝对时刻。 |
| 时区绑定时间 | 按绑定时区 A 的规则不变，在 B 中显示对应本地换算。 |
| 绝对时刻 | Instant 不变，在 B 中只改变显示。 |

已经发生或用户处理的历史实例不重算。未来提醒必须取消旧系统调度并按新结果对账；同一逻辑提醒保持去重键。

### REC-023：设备时钟异常

- 发现当前时钟比上次持久化可信时刻倒退超过 5 分钟时，显示非阻断诊断状态并暂缓自动永久清理、配额重置和大批历史实例生成。
- 用户仍可以创建本地记录；保存用户声明的日期时间并使用单调序列维持写入顺序。
- 时钟恢复后重新计算未来关注项，不能改写已保存 createdAt、流水时间或完成时间。
- 服务端可以根据接收时间识别异常，但不能静默替换用户业务日期。

## 4. 自然日、周和到期

### REC-030：自然日边界

用户当前时区的 `[00:00, 下一日 00:00)` 是一个自然日。不能用固定 24 小时计算“今天”，因为夏令时日可能为 23 或 25 小时。

### REC-031：周起始日

- 周起始日默认来自地区设置，用户可以改为周一或周日。
- “每 N 周”的锚点使用创建时保存的 `weekStart`，之后改变全局设置不改写已有规则。
- 日历显示可以使用当前偏好，但规则预览必须按规则自身 weekStart。

### REC-032：逾期判断

| 对象 | 派生为逾期的时点 |
| --- | --- |
| 有时间的周期实例 | 当前 Instant 严格晚于 effective schedule 的解析 Instant，且仍 pending。 |
| 全天周期实例 | effective local date 的下一日 00:00，且仍 pending。 |
| 有时间的开放清单 | 当前 Instant 严格晚于 due schedule。 |
| 仅日期开放清单 | 截止日期的下一日 00:00。 |
| 备忘 | 从不把备忘标为逾期；过时未确认提醒进入“待查看”。 |
| 重要日期 | 从不标为逾期；过去发生项只成为历史。 |
| 低库存 | 是状态，不使用逾期。 |

刚好等于截止时刻时视为已到时但不使用“晚了 N 分钟”的文案；下一分钟开始显示逾期时长。

### REC-033：相对天数文案

- “今天/明天/还有 N 天”按本地日历日差计算，不按秒数除以 86,400。
- “N 小时后”按绝对持续时间计算。
- 到期日在今天时不显示“0 天后”；使用“今天到期”。
- 过去重要日期不显示负数天，进入历史文案。

## 5. 夏令时与时区数据库

### REC-040：不存在的本地时间

浮动或时区绑定时间落在春季跳时的空隙时，采用“兼容”策略：按空隙长度向后平移到第一个对应有效时间。

示例：某时区从 02:00 跳到 03:00，计划 02:30 的发生项在当天解析为 03:30，并在详情标注因夏令时调整。后续正常日期仍为 02:30，不能永久改写规则。

### REC-041：重复的本地时间

秋季回拨造成同一钟表时间出现两次时，默认选择较早的 Instant，只产生一个发生项和一个提醒。`ScheduleSpec.disambiguation` 保存 `earlier`；未来高级导入可以显式选择 `later`，但 P0 UI 不要求开放。

### REC-042：时区数据库升级

- 发布构建必须记录使用的时区数据库版本。
- 版本升级后只重算尚未发生的浮动/时区绑定事件和提醒。
- 历史实例保留当时解析出的 Instant、时区 ID 和规则版本。
- 如果未来结果变化，重新对账并在受影响详情提供非阻断说明；不得重复通知。

## 6. 重复规则结构

### REC-050：`RecurrenceRule`

规则逻辑字段：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `frequency` | `daily \| weekly \| monthly \| yearly` | 必填。 |
| `interval` | 1–999 整数 | “每隔 N 个频率单位”；1 表示每个单位。 |
| `byWeekdays` | 星期集合 | weekly 时至少一个；其他频率 P0 不使用。 |
| `byMonthDays` | 1–31 的去重有序集合 | monthly 时至少一个；P0 不含“最后一天”特殊值。 |
| `yearMonthDay` | 月、日 | yearly 使用；默认来自开始日期。 |
| `endMode` | `never \| until \| count` | 必填。 |
| `untilDate` | `LocalDate?` | until 时必填，包含边界。 |
| `occurrenceCount` | 1–100000? | count 时必填，计算实际产生的候选项。 |
| `weekStart` | `monday \| sunday` | weekly 保存快照。 |

集合输入在保存前排序和去重。同一天不得因为重复条件产生两个发生项。

### REC-051：开始边界

- `effectiveFrom` 是包含边界。
- 如果开始日期符合规则，它是第一个候选项。
- 如果不符合，选择开始日期之后第一个符合项。
- 开始日期在过去时不改变规则；历史显示和物化按 REC-080 处理。

### REC-052：结束日期

- `untilDate` 是包含边界：候选本地日期 `<= untilDate` 时有效。
- untilDate 早于第一个有效候选日期时规则校验失败，不能保存一个永远不发生的系列。
- 时间区和夏令时不改变日期包含关系。

### REC-053：重复次数

- count 表示规则实际产生的候选发生项总数，包含第一个有效发生项。
- 因月日不存在而跳过的月份/年份不计数。
- 用户后来完成、跳过、取消或改期的发生项仍计入原规则段的 count，因为候选项已经存在。
- 本次及以后切分时，新规则段拥有独立结束条件；界面必须预览剩余次数，不能沿用含糊旧总数。

## 7. 各频率算法

### REC-060：每天与每隔 N 天

以 `effectiveFrom` 为第 0 个锚点。日期 `D` 符合条件当且仅当：

```text
daysBetween(effectiveFrom, D) >= 0
and daysBetween(...) mod interval = 0
```

使用日历日差，不使用两个 Instant 的小时差。

### REC-061：每周指定星期

1. 找到包含 `effectiveFrom` 的锚点周，周起始使用规则保存的 weekStart；
2. 只有与锚点周相差周数能被 interval 整除的周有效；
3. 在有效周内按 `byWeekdays` 产生日期；
4. 丢弃早于 effectiveFrom 的日期；
5. 同周按日历先后排序。

如果用户选择“每周”但没有明确星期，默认使用开始日期的星期，并在确认中显示。

### REC-062：每月指定日期

1. 以 effectiveFrom 所在年月为第 0 个锚点月；
2. 只有相差月数能被 interval 整除的月份有效；
3. 为每个 byMonthDays 生成合法日期；
4. 某月不存在指定日期时**跳过该日期**，不自动夹到月末；
5. 丢弃早于 effectiveFrom 的日期并去重排序。

示例：每月 31 日在 2、4、6、9、11 月不发生。P0 不支持“每月最后一天”；智能输入遇到该表达时转手动并说明当前限制，不偷偷解释为 31 日。

### REC-063：每年指定月日

1. 以 effectiveFrom 年为第 0 个锚点年；
2. 只有相差年数能被 interval 整除的年份有效；
3. 生成指定月日，丢弃早于 effectiveFrom 的候选；
4. 2 月 29 日在非闰年**跳过**，不自动改为 2 月 28 日或 3 月 1 日。

若用户需要每年二月最后一天，必须等支持相应规则后明确选择。

### REC-064：顺序与去重

候选项以“规则段 ID + 原始本地日期 + 原始本地时间/全天标志”为稳定身份。多个条件命中同一值时只产生一次。排序先按本地日期时间，再按稳定键；解析到相同 Instant 也不得合并不同业务实例。

## 8. 规则修改与实例

### REC-070：预览

创建或修改重复规则时必须预览至少接下来的 5 个有效发生项；有效项不足 5 个时展示全部，并明确结束条件。预览使用与保存后相同的规则引擎和时区数据库，不能另写简化算法。

### REC-071：仅本次改期

- 原始计划保留在 occurrence identity 中。
- 新计划按自身时间行为解析，默认继承系列时间行为。
- 改期到过去时允许保存，但立即派生 overdue，并不补发已经过去的系统通知。
- 改期跨越系列结束日期仍只影响本次，不延长规则总数。
- 改期后与另一发生项同一天/同一时刻时，两项独立显示并说明来源。

### REC-072：本次及以后切分

设目标原始日期为 `T`：

1. 旧规则段 `effectiveUntil` 设为 `T` 前一日历日，或采用排除 T 的等价边界；
2. 新规则段 `effectiveFrom` 由用户确认，通常为 T；
3. 已物化的 T 及未来未处理实例按新规则重算或取消，已完成/跳过/取消历史不改变；
4. 旧段和新段的候选身份不得碰撞；
5. 新规则预览必须显示切分后首 5 项。

同一天有多个时间的未来扩展不能用简单“前一日”切分，物理实现必须以完整候选键为边界；P0 一条重复事项每天至多一个计划时刻。

### REC-073：全局时间设置变化

- 修改周起始日只影响新规则和日历显示，不改写已有 weekly 锚点。
- 修改默认全天提醒时刻只影响新提醒计划。
- 修改当前时区按 REC-022 重算未来值。
- 语言和日期显示格式不改变任何候选日期。

## 9. 发生项计算与物化

### REC-080：查询窗口

规则引擎接收明确的闭开区间 `[from, to)` 并以分页方式返回候选项，不依赖“现在”。调用方分别选择窗口：

- 今天聚合：覆盖当前自然日、即将到来窗口，以及发现逾期所需的上次处理游标；
- 提醒调度：覆盖提醒规范定义的未来滚动窗口；
- 历史列表：按用户请求的日期页计算；
- 结束次数验证：从规则开始按页计数到结束或上限。

不得为了方便在创建规则时物化无限未来。

### REC-081：逾期游标

每个活跃规则段保存一个非权威计算游标，用于知道从哪里继续扫描未处理过去候选：

- 游标可以删除并从规则与终态实例重建；
- 扫描结果按 BR-042 聚合，不要求把全部未处理候选立即写成行；
- 用户处理某个计算候选时才物化对应 Occurrence；
- 计算必须分页，单次前台刷新最多处理 500 个候选，剩余在后台/后续帧继续并显示“正在整理较早记录”；
- 不得因为达到 500 就把更早候选当作完成或跳过。

### REC-082：历史事实

以下情况必须物化并长期保留 occurrence：

- 用户完成、跳过、取消、改期或添加仅本次说明；
- 已为其创建提醒实例或收到通知动作；
- 同步、审计或冲突引用该发生项；
- 规则切分需要保护它不被重算。

未互动且仍可由当前规则确定性计算的候选可以只作为投影存在。

### REC-083：发生项过期与保留

- pending 候选不会因时间过去自动变成 skipped。
- 没有用户状态、没有提醒历史且不再需要展示的计算投影无需持久化。
- 已物化历史跟随根记录生命周期和数据保留规则。
- 修改规则引擎版本时用固定测试向量和已保存 original schedule 验证，不能重写旧历史以匹配新算法。

## 10. 重要日期算法

### REC-090：公历仅一次

保存完整 `LocalDate`。当前日期等于它时为今日；未来日差按 REC-033；过去后成为历史，不自动删除或归档。

### REC-091：公历每年

每个目标年份使用保存的月日生成一个 DateOccurrence：

- 合法日期正常生成；
- 2 月 29 日在非闰年跳过；
- startYear 只用于计数，不作为结束年份；
- 目标年份早于 startYear 时不生成发生项，也不显示年龄/周年；
- 同一年同一重要日期只有一个 occurrenceKey。

### REC-092：农历扩展

P0 不解析、保存或近似换算农历值。P1 只把中国农历用于 `important_date` 的 `once | yearly`，不能把它加入通用任务重复 kernel。

原始值必须按重复方式保存：

| 模式 | 原始值 | 策略规则 |
| --- | --- | --- |
| `once` | 农历年、月、日、`isLeapMonth`、`conversionRuleVersion` | 不使用年度 fallback；闰月缺失策略必须为空。 |
| `yearly` | 农历月、日、`isLeapMonth`、可选农历 `startYear`、`conversionRuleVersion` | 仅 `isLeapMonth=true` 时必须有 `leap_month_only \| regular_month_when_missing`。 |

原始农历字段不能被换算后的公历日期覆盖。`eventKind`、历法、重复方式和 `startYear` 保持正交。

### REC-093：一次性农历日期

保存前必须由记录指定的转换规则版本验证农历年、月、日与 `isLeapMonth` 的完整组合真实存在，并能唯一换算成支持范围内的公历日期。组合不存在是字段校验失败；年份超出该版本公开支持范围是 unsupported。两者都不能保存，也不能应用年度闰月 fallback、夹到月末、顺延或近似换算。

### REC-094：每年农历候选算法

对目标农历年 `Y` 按下列顺序计算，任何步骤都不得交换：

1. `startYear` 存在且 `Y < startYear` 时不生成发生项；
2. `isLeapMonth=false` 时只选择同月号普通月，即使 `Y` 还有同号闰月也不重复；
3. `isLeapMonth=true` 且 `Y` 存在同号闰月时选择该闰月；
4. `isLeapMonth=true` 且 `Y` 不存在同号闰月时，`leap_month_only` 不选候选月，`regular_month_when_missing` 选择同号普通月；缺失、未知或不受支持的策略标记“需要确认”，不生成候选；
5. 选出候选月后才验证原始日；候选月没有该日时该年不发生，不夹月末、不顺延、不跨月；已经选中但缺日的闰月不得再退回普通月；
6. 用记录的 `conversionRuleVersion` 换算并保存解析结果；同一记录在同一目标农历年最多产生一个 `DateOccurrence`。

TD-028 负责把上述语义映射为具体 adapter、支持年份、版本身份和 occurrence identity；实现不得在 TD-028 或合同之外增加地域默认。

### REC-095：无发生年份不是业务状态

因同名闰月不存在、候选月缺日或早于 `startYear` 而无候选时：

- 不物化 `DateOccurrence`，也不创建或调度提醒；
- 根重要日期保持有效，不产生 `skipped`、`completed` 或 `overdue`；
- “下一次”向后扫描下一个有效农历年，并受 adapter 支持范围与 REC-121 计算预算限制；
- 界面可以解释“该年不发生”，但不能把它显示为数据损坏或要求用户处理的逾期项。

### REC-096：起始年份、计数与展示

农历记录的 `startYear` 是农历年。年龄或周年数等于 `目标农历年 - startYear`，不是累计实际发生次数；没有 `startYear` 时不显示计数，也不推断虚岁。无发生年份不显示该年计数，下一个有效年份的计数可以跨年跳增。

确认、详情与下一次预览同时显示原始农历日期和当前规则解析出的公历日期。使用 `regular_month_when_missing` 且本年实际采用普通月时必须可见说明；没有有效年份时显示范围和原因，不伪造公历结果。

### REC-097：编辑、版本与历史

- 修改原始日期、`startYear` 或闰月策略，只取消并重建未来发生项和未来提醒；已物化历史保留当时的原始值、实际采用的普通/闰月、换算后公历日期和规则版本。
- 转换规则升级只重算未来。支持年份范围必须公开，兼容版本不得静默缩小；范围外返回 unsupported。
- 导入、智能草稿或旧数据的策略缺失/未知时标记“需要确认”，在用户确认前不生成发生项或提醒；不得迁移成任一默认策略。
- 切换公历与农历视为重新输入日期，必须重新校验并预览，不能复用旧历法的裸数字。

## 11. 提醒偏移的时间语义

### REC-100：日历偏移与持续时间偏移

| 用户表达 | 计算方式 |
| --- | --- |
| 提前 N 天/周/月 | 在来源本地日历上减去对应单位，再使用提醒时刻解析；不是固定秒数。 |
| 提前 N 小时/分钟 | 从来源解析后的 Instant 减去绝对持续时间。 |
| 当天 09:00 | 在来源本地日期使用 09:00 和来源时间行为。 |
| 绝对指定提醒 | 独立 ScheduleSpec，不依赖业务时间偏移。 |

例如跨夏令时“提前 1 天 09:00”仍是前一个本地日 09:00，可能与业务时刻相差 23 或 25 小时。

### REC-101：偏移落在过去

- 创建记录时某个提前提醒已经过去：不补发，确认页标记“已错过”并默认关闭该提醒实例；用户可以改为现在、稍后或删除计划。
- 编辑导致未来提醒变成过去：取消旧调度，不立即发送。
- 当天业务日期仍可以在今天出现，不因提前提醒已错过而消失。

### REC-102：提醒先于记录开始

重复事项的提醒偏移不得产生早于规则段 effectiveFrom 所代表首次业务发生的提醒，除非用户在确认页明确允许“开始前准备提醒”。P0 默认不允许负向越过系列开始。

## 12. 自然语言时间解释

### REC-110：参考时刻固定

一次智能创建会话从首次提交起固定 `referenceInstant`、`referenceTimeZone` 和 `locale`。追问答案使用同一参考上下文，不能因为跨午夜或请求重试把“明天”解析成不同日期。

### REC-111：确定表达

以下表达可以直接解析并在确认页展示：

- 今天、明天、后天；
- 明确年月日；
- 明确星期且上下文能唯一选择最近未来日期；
- 明确“每周日”“每隔两天”等受支持规则；
- 明确时刻或 REC-012 的可建议时段。

如果“周日”在当前日当天且所指过去/今天/下周不清楚，优先生成今天仍未过时的未来时刻；否则取下一周，并在确认页显示完整日期。

### REC-112：必须追问或转手动

以下不能静默猜测：

- 下周、月底、过几天、晚点等无法唯一确定日期；
- “每月最后一天”等 P0 不支持规则；
- 睡前、饭后、到家时等没有确定时刻或事件来源；
- 同一句话出现互相冲突的日期/时区；
- 结束“一个月”到底按自然月还是 30 天影响结果且无法从语境判断；
- 日期已过去但用户使用将来语气。

P0 只有一次追问机会；仍不明确时携带原输入转到手动表单。

## 14. 算法版本与兼容

### REC-120：规则版本

每个持久化规则段保存 `recurrenceEngineVersion`。兼容性规则：

- 修复只影响未来未物化候选时可以升级版本并预览差异；
- 可能改变历史候选身份的修复必须保留旧引擎解释器或迁移成显式实例；
- 备份恢复必须带回规则版本；
- 服务端同步不能用不同算法静默重算客户端已经物化的 original schedule。

### REC-121：计算上限

- 单次规则预览最多扫描 10,000 个候选周期；超过说明规则过稀或结束条件不可达，要求修改。
- 单规则最多 occurrenceCount 100,000。
- 大范围历史和提醒计算分页执行，可取消并继续。
- 计算上限只能返回明确错误或部分进度，不能截断后声称完整。
