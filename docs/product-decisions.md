## 决策状态

- **已确认**：产品规划与实现应遵守，修改前需要重新讨论。
- **待讨论**：尚未形成结论，不应当被写成既定方案。

## 已确认决策

### PD-001：手机 App 优先

- 状态：已确认
- 确认日期：2026-07-21

#### 决定

P0 以手机 App 为主，同时支持 iOS 和 Android。Web 端后置，不纳入 P0。

#### 原因

- 快捷记录和随手查看主要发生在手机上。
- 系统通知是重复事项和重要日期的核心体验。
- 语音、拍照、扫码及家庭物品盘点更适合移动设备。
- P0 同时开发完整 Web 端会扩大范围，延迟首个可用版本。

#### 产品影响

- P0 页面与交互优先按手机尺寸设计。
- 提醒能力优先使用移动操作系统通知。
- Web 端以后用于批量整理、查看和跨设备访问，不作为首发前置条件。

### PD-002：免登录、本地优先

- 状态：已确认
- 确认日期：2026-07-21

#### 决定

用户无需注册或登录即可使用完整的 P0 手动功能。生活记录以本地数据为主，账号、云备份和跨设备同步在后续版本提供。

#### 原因

- 首次打开即可记录，避免注册流程造成流失。
- 没有网络时仍能创建、修改、搜索和处理记录。
- 私密生活数据默认留在用户设备中。
- 模型服务不可用时，核心手动功能仍可使用。

#### 版本边界

- P0：本地数据、离线使用、加密备份、恢复和导出。
- P1：账号、加密云备份和跨设备同步。
- P2：依赖账号与同步的家庭成员协作。

#### 产品影响

- 本地数据不能只是云端缓存，而应支持完整业务操作。
- 智能创建是需要联网的可选能力，不能成为手动功能的依赖。
- 数据模型从 P0 开始预留空间、所有者和修改人的概念。

### PD-003：个人空间默认私密，家庭空间主动共享

- 状态：已确认
- 确认日期：2026-07-21

#### 决定

每位用户始终拥有一个默认私密的个人空间。家庭共享上线后，用户可以创建或加入家庭空间；只有主动放入家庭空间的记录才会与成员共享。

#### 原因

- 加入家庭不应改变已有私人记录的可见范围。
- 备忘、纪念日和家庭库存可能具有不同的隐私需求。
- 明确选择空间比逐条配置复杂权限更容易理解。

#### 家庭空间基本规则

- 个人记录不会因为加入家庭而自动迁移或共享。
- 家庭库存、采购清单和共同事项可以放入家庭空间。
- 家庭成员可以共同处理共享清单、事项和库存。
- 重要修改保留操作人、操作时间和变更内容。
- 家庭创建者负责邀请、移除成员及高风险管理操作。
- 普通成员可以查看、新建和编辑家庭空间中的共享记录。
- 删除家庭空间、批量删除等高风险操作只允许家庭创建者执行。
- 第一阶段不设计复杂的逐条成员权限。

#### 产品影响

- 所有记录都必须明确归属于一个空间。
- 个人空间与家庭空间在界面中必须容易区分。
- 从个人空间移动到家庭空间属于共享行为，需要明确确认。

### PD-004：默认提醒一次，不连续催促

- 状态：已确认
- 确认日期：2026-07-21

#### 决定

提醒到达设定时间时默认尝试发送一次系统通知。用户没有处理时，适用的关注项继续在“今天”显示，但只有具有完成或截止语义的对象显示为逾期。系统不默认连续发送通知；需要重复催促时，由用户明确开启并设置间隔。

#### 原因

- 产品应当可靠提醒，但不通过高频通知制造焦虑。
- 未处理与未看到是不同问题，应用内状态比重复推送更适合长期保留。
- 医疗、出发等特殊场景确实需要连续提醒，应当由用户主动决定。

#### 具体规则

- 系统通知只提供适合其来源类型的快捷操作；完成和跳过不泛化到备忘、重要日期或低库存状态。
- 稍后提醒提供常用时间并允许自定义。
- 重复事项的每个周期相互独立，本次逾期不阻止下一次生成。
- 重要日期允许设置多次提前提醒。
- 低库存只在首次进入不足状态时提醒；补货恢复后再次不足，才重新提醒。
- 没有系统通知权限时，提醒仍在应用内可见，并说明如何开启权限。
- 应用不得擅自改变用户明确设置的提醒时间，但不能承诺绕过操作系统勿扰、通知摘要、权限、设备关机或厂商省电限制。
- 系统建议、回顾等非用户明确设置的通知遵守应用静默时段。

### PD-005：内置模型服务为主，自带 API Key 为补充

- 状态：已确认
- 确认日期：2026-07-21

#### 决定

普通用户直接使用内置的智能创建服务，不需要理解模型名称或配置 API Key。系统通过统一适配层接入 GPT、千问等供应商。后续为高级用户提供自带 API Key 和兼容接口配置。

#### 原因

- 智能创建应当是产品能力，而不是要求普通用户完成的技术配置。
- 统一适配层可以避免被某一家模型供应商绑定。
- 自带 Key 为高频用户和私有部署保留选择，也有助于控制平台成本。

#### 产品规则

- 默认由系统选择可用模型，不要求用户每次选择供应商。
- P1 高级设置可以展示供应商并允许配置自带 Key。
- 模型切换不能影响已有数据、草稿结构和确认页面。
- 内置智能创建可以设置免费额度，正式收费方式另行讨论。
- 智能额度用完或模型不可用时，所有手动功能仍保持可用。
- 当前创建会话中的用户输入不能因为模型调用失败而丢失；P0 不承诺在用户主动退出或操作系统终止 App 后继续保存未确认草稿。

#### 模型数据边界

- P0：只发送本次输入、当前日期、用户时区和必要字段定义。
- P1：用户可以主动选择某条已有记录作为参考上下文。
- P2：模型可以提出修改已有记录的草稿，但仍需用户逐项确认。
- 敏感记录可以明确禁止用于任何智能功能。
- 模型不能直接访问或写入生活簿数据库。

### PD-006：隐私和可恢复性是基础能力

- 状态：已确认
- 确认日期：2026-07-21

#### 决定

生活数据默认私密。P0 同时提供设备内保护、敏感内容控制、加密备份和恢复能力，不能把数据安全推迟到云同步阶段。

#### 设备内保护

- 数据保存在应用私有目录。
- 用户可以通过 Face ID、指纹或设备密码锁定应用。
- 单条记录可以标记为敏感内容。
- 敏感记录的系统通知在 P0 不展示标题和正文；全局通知内容设置不能降低这一保护。
- 用户可以统一选择通知显示完整内容、只显示标题或完全隐藏。

#### 数据使用保护

- 模型处理本次原始输入所必需的传输不等同于日志留存。生活有谱的业务数据库、错误日志和数据分析不得记录完整原始输入或备忘正文。
- P0 产品内置供应商 API Key 只存在服务端密钥系统。P1 用户自带 Key 使用设备安全存储。两者都不得进入普通数据库、日志或代码仓库。
- 必须明确区分本地数据、云端数据、家庭共享数据和发送给模型的数据。

#### 备份与删除

- P0 支持创建加密备份文件并从备份恢复。
- 可以导出可阅读数据，但导出前明确提示文件未加密。
- 删除的记录默认进入回收站并保留 30 天。
- 永久删除、清空回收站、清除本机数据和删除家庭空间需要二次确认。
- 默认个人空间实体始终存在，P0 不提供“删除个人空间”；清除本机数据后重新建立空的默认个人空间。
- P1 云同步采用传输加密和服务端存储加密。
- 端到端加密的具体范围暂不承诺，在同步与家庭共享架构确定后单独评估。

### PD-007：围绕减少记忆负担的个人用户设计 P0

- 状态：已确认
- 确认日期：2026-07-22

#### 决定

P0 的核心用户是经常需要记住生活琐事、准备各种清单和管理家中物品，但不喜欢复杂效率工具的个人用户。

产品的第一核心场景是：

> 用户想到一件生活小事，点击加号，用一句话记录，确认后在正确时间再次看到它。

#### 典型需求

- 容易忘记周期性家务和生活事项。
- 出行时经常重新整理准备清单。
- 害怕错过生日、纪念日和证件到期。
- 不清楚家里某种用品还有多少。
- 希望一句话记下来，而不是研究复杂表单。
- 想减少记忆负担，而不是追求任务完成率。

#### 核心体验链路

```text
快速记下
→ 自动整理
→ 用户确认
→ 准时出现
→ 长期可查
```

#### 产品影响

- 首页优先展示需要关注的内容，不优先展示统计图和完成率。
- 全局加号和智能创建是首个关键体验，不隐藏在多层菜单中。
- 新手引导应尽快帮助用户创建第一条真实记录。
- 产品文案强调安心、清楚和有着落，避免绩效、排名和自律压力。
- 清单模板和家庭库存承担长期留存价值。
- P0 首页优先回答“今天有什么要做”“最近有什么不能忘”“家里有什么需要补充”。

### PD-008：首次使用采用渐进式引导

- 状态：已确认
- 确认日期：2026-07-23

#### 决定

首次打开不强制注册、不展示教程轮播，也不一次性申请多个系统权限。用户直接进入可创建第一条真实记录的页面，权限、隐私和备份说明在对应场景首次发生时出现。

#### 首次体验目标

- 用户能够在一分钟内开始创建第一条真实记录。
- 首屏同时提供一句话创建和五种手动创建入口。
- 使用贴近日常的示例提示，但不自动写入虚假示例数据。
- 空页面通过真实操作引导用户，不使用无意义的占位内容。

#### 权限申请规则

- 创建第一条带时间的记录时，再解释并申请通知权限。
- 用户主动开启应用锁时，再申请 Face ID、指纹或设备验证权限。
- P1 使用语音输入时，再申请麦克风权限；P0 不申请麦克风权限。
- 添加图片时，再申请相册或相机权限。
- 开启云同步时，再引导注册和登录。
- 用户拒绝权限后，相关流程不能卡死，并提供重新开启权限的入口。

#### 智能创建首次说明

首次使用智能创建时说明：本次输入会发送给智能服务，默认不会发送生活簿中的其他记录，确认前不会写入生活记录数据库。用户确认一次后记住选择，敏感记录继续遵守更严格的独立设置；请求处理、供应商留存和日志边界必须在隐私说明中分别表述。

#### 成功反馈

创建成功后展示具体结果，例如记录标题、执行时间和提醒时间，而不是只显示“创建成功”。用户可以继续查看记录、再记一件或返回今天。

#### 备份提示

不在首次启动时要求用户理解备份。用户已经创建至少一条真实记录，并达到累计创建 5 条真实记录或安装满 7 个自然日中的任一条件后，再首次温和提示创建加密备份。真实记录指用户手动保存或确认智能草稿后创建的记录，不包括模板内置内容、恢复或导入的数据；删除记录不回退累计计数。用户关闭提示后至少 30 天不再次主动提示。

### PD-009：记录类型决定状态和可执行动作

- 状态：已确认
- 确认日期：2026-07-26

#### 决定

五种记录共享创建、查找、分类、标签、归档和删除等基础能力，但不共享同一套业务状态和快捷动作。界面与系统通知必须根据具体来源展示动作。

#### 原因

- 重复事项周期实例可以完成或跳过；清单及其项目可以完成，但备忘没有完成状态。
- 重要日期描述一个日历事实，家庭物品的低库存描述一个派生状态，把它们标记为完成会损害历史语义。
- “提醒是否处理”与“记录是否完成”是两个不同状态，不能为了统一按钮而合并。

#### 产品影响

- “今天”使用关注项聚合不同对象，但卡片动作由业务规则矩阵决定。
- 系统通知的动作类别必须与来源类型一致。
- 领域模型分别保存记录生命周期、周期实例状态、清单进度和提醒实例状态。

### PD-010：低库存采用包含阈值的判断

- 状态：已确认
- 确认日期：2026-07-26

#### 决定

家庭物品当前数量**小于或等于**最低库存时进入低库存状态。库存流水是数量变化的历史事实，不直接编辑或删除；发现错误时使用新的调整流水修正。

#### 原因

- “最低库存”表示希望至少保有的数量，刚好达到该数量时已经需要关注补货。
- 不可变流水能够解释当前数量、同步并发变化和误操作修正。
- 单独修改最终数量会失去变化原因，并增加未来家庭协作的冲突风险。

#### 产品影响

- 所有界面统一使用“不多于最低库存”或“剩余 N，建议补货”，不使用与规则冲突的“少于 N 才提醒”。
- 创建物品时以期初库存流水记录初始数量。
- 同一低库存周期只主动提醒一次，恢复到阈值以上后再次进入低库存才开启新周期。

### PD-011：P0 智能追问最多一轮

- 状态：已确认
- 确认日期：2026-07-26

#### 决定

P0 智能创建最多提出一轮、一个关键问题，回答后只生成一条草稿。回答后仍存在关键歧义、用户不回答或原始输入包含多个独立意图时，引导用户选择并完成一条记录的手动表单。P1 才提供保留上下文的多轮追问和一次生成多条草稿。

#### 原因

- P0 的目标是快速创建，不是建立完整聊天体验。
- 限制轮次使交互、状态恢复、模型成本和评测范围可控。
- 对关键日期、时间和数量不猜测，比连续追问更符合用户确认原则。

#### 产品影响

- P0 服务契约只需要“草稿、一个追问、无法识别”三种业务结果。
- 追问答案与原始输入在同一临时会话中使用，不形成聊天历史。

### PD-012：恢复、导入和分享是不同能力

- 状态：已确认
- 确认日期：2026-07-26

#### 决定

P0 支持从本产品加密备份进行**整体恢复**，以及导出结构化或可阅读文件；不支持把任意外部数据合并到当前生活簿。带预览、字段映射和冲突处理的通用导入属于 P1。单条清单分享和家庭空间共享分别按路线图交付，不与全量导出混称。

#### 原因

- 整体恢复可以在替换前完整校验并保持数据一致性。
- 通用导入需要映射、去重、附件处理和冲突界面，会显著扩大 P0。
- 分享、导出、恢复和同步具有不同的隐私与生命周期后果。

### PD-013：移动系统边界内的可靠提醒

- 状态：已确认
- 确认日期：2026-07-26

#### 决定

生活有谱保证业务规则计算和本地调度可验证、可对账；对已经成功交给操作系统调度的提醒支持离线触发。产品不承诺绕过操作系统权限、勿扰、通知摘要、设备关机、厂商省电或后台执行限制，也不承诺用户长期不打开 App 时任意复杂重复规则无限期准点。

#### 原因

- iOS 和 Android 对后台执行、待调度通知数量与精确提醒权限存在平台约束。
- 无法由产品控制的绝对承诺会造成错误安全感。
- 通过滚动调度、前台对账和清楚状态，可以在本地优先前提下提供可理解的可靠性。

#### 产品影响

- App 每次启动、回到前台、规则修改、时区变化、权限变化和版本升级时重新对账未来提醒。
- Android 精确提醒权限被拒绝时明确降级为近似提醒，不阻塞记录创建。
- 内容设计和支持文档必须说明平台边界，验收测试区分“业务计算正确”“已交给系统”和“最终可见”。

### PD-014：内置模型按发行地区启用

- 状态：已确认
- 确认日期：2026-07-26

#### 决定

系统保持 GPT、千问及其他兼容供应商的统一适配能力，但生产环境只在供应商条款和发行地区允许时启用对应模型。中国大陆环境默认使用合规可用的国内供应商；GPT 适配存在不代表在所有地区向用户开放。

#### 原因

- 模型供应商的可用地区、数据处理条款和监管要求不同且会变化。
- 把某一模型写成所有地区的固定依赖，会破坏手动功能独立和多供应商目标。
- 用户需要稳定的产品行为，不需要理解每次供应商切换。

#### 产品影响

- 服务端按地区、功能开关、健康状态和额度路由供应商。
- 草稿契约、确认页面和已有数据不依赖供应商名称。
- 发布前第三方服务清单必须反映实际地区启用的供应商。

### PD-015：通用数据结构不等于 P0 全部开放

- 状态：已确认
- 确认日期：2026-07-26

#### 决定

领域模型可以为五种记录预留分类、标签、敏感标记、附件和关联等通用结构，但 P0 界面只开放路线图明确列出的类型能力。预留字段不得被描述为已经交付的用户功能。

#### 原因

- 稳定的通用结构可以减少未来迁移。
- 同时把所有通用能力开放给所有类型会扩大页面、权限、备份和测试组合。
- 产品范围应由用户可见能力决定，而不是由数据库是否已经有字段决定。

#### 产品影响

- 产品功能说明维护“能力是什么”，路线图唯一维护“在哪一期开放”。
- 页面规格必须按阶段和记录类型展示字段，不根据数据表自动生成全部入口。
- 智能草稿不能填充当前阶段不允许用户确认的字段。

### PD-016：默认个人空间始终存在

- 状态：已确认
- 确认日期：2026-07-26

#### 决定

安装后立即创建一个默认个人空间，并在 P0 生命周期内始终保留该空间实体。用户可以清除全部本机生活数据，清除完成后系统重新建立空的本地身份和默认个人空间。P2 家庭空间可以由家庭创建者按高风险流程删除。

#### 原因

- 所有记录必须有稳定空间归属，P0 又没有第二个空间可以切换。
- 把清空内容称为删除空间，会让未来账号认领和家庭空间语义混乱。
- 清除本机数据仍应让 App 回到可立即使用的初始状态。

### PD-017：不在商业模式确定前承诺永久免费

- 状态：已确认
- 确认日期：2026-07-26

#### 决定

在正式商业模式形成前，不对外承诺任何能力“永久免费”。无论额度或收费如何设计，内置智能服务不可用时，用户仍能访问自己的已有数据，并使用当前版本已经提供的本地手动能力。

#### 原因

- 数据可访问性和智能服务计费是两个不同问题。
- 过早承诺永久价格会限制可持续运营选择。
- 用户不应因外部模型成本或故障失去本地数据和基础操作。

### PD-018：P1 农历重要日期保留原历法并显式选择闰月策略

- 状态：已确认
- 确认日期：2026-07-27

#### 决定

P0 仍只接受公历重要日期。P1 把中国农历支持限定在“重要日期”的一次或每年发生，不把农历扩展成通用任务重复规则。系统必须保存用户输入的农历年/月/日、是否闰月、闰月缺失策略及转换规则版本，不能只保存某一年的公历换算结果。

每年发生的普通农历日期只使用同月号普通月；即使同年还有同名闰月，也不能生成第二个发生项。用户创建或编辑闰月日期时，必须在下列策略中明确选择一项，产品不得暗设地域习惯：

1. **仅在同名闰月出现**：目标年份没有该闰月时不生成发生项；
2. **无闰月时使用同名普通月**：有同名闰月时使用闰月，没有时使用同月号的普通月。

年度解析顺序固定为：先按闰月标记和上述策略选择候选月，再验证候选月是否存在原始日期，最后为一个目标农历年生成至多一个发生项。候选月没有该日时，该年不发生；不能夹到月末、顺延、跨月，也不能从存在但缺少该日的闰月退回普通月。

一次性农历日期必须包含农历年、月、日和闰月标记，并在所选转换规则版本下真实存在；无效组合不得保存。每年农历日期的 `startYear` 表示农历年，年龄或周年数按“目标农历年减 `startYear`”计算，而不是累计实际发生次数；没有 `startYear` 时不显示计数，不推断虚岁。某年不发生时不生成 `DateOccurrence`、不调度提醒，也不产生跳过、完成或逾期状态；根记录仍然有效，下一次展示前进到下一个有效年份，计数可以跨年跳增。

智能创建、导入或旧数据无法确定闰月策略，或者遇到未知策略版本时，必须标记“需要确认”，不得生成发生项或提醒，也不能猜测默认值。确认页和详情页应同时显示原始农历日期与当前规则计算出的公历日期，并把“该年不发生”呈现为规则结果而不是数据错误。

编辑原始日期或闰月策略只重算未来发生项并取消、重建未来提醒；已经物化的历史结果保留当时的原始值、策略版本和解析结果。转换规则版本升级同样不得重写历史。支持年份范围由 TD-028 固定并向用户公开；范围不得在兼容版本中静默缩小，范围外一律返回 unsupported，不作近似换算。

#### 原因

- 农历日期的用户意图是原历法事实；只保存换算后的公历日期会在后续年份失真。
- 闰月生日或纪念日没有对所有用户都正确的单一习惯，显式选择比按地区猜测更可靠。
- 月内不存在指定日时自动夹到月末会悄悄改变用户选择，跳过更可解释、也与公历 2 月 29 日策略一致。
- 把能力限制在重要日期，可以隔离 P0 重复引擎和提醒语义，避免把所有农历周期提前承诺到 P1。

#### 产品影响

- `PR-260` 的 P1 切片只增加农历重要日期，不改变 P0 公历数据和 occurrence 身份。
- 时间规范负责发生项语义；领域模型保存原始历法字段和策略；页面、内容与无障碍规范必须让两种闰月策略可理解且可修改。
- 智能创建在没有明确闰月策略时返回追问或 unsupported；不得把农历数字当作公历。
- 技术实现必须使用独立 ADR（预留 TD-028）固定历法数据来源、版本、支持年份、转换 adapter、升级迁移、occurrence identity 与跨实现 oracle；该 ADR 和对应合同未通过前，P1 农历入口保持关闭。
