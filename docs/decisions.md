# 决策记录

> 只记录会影响方向、范围或架构的决定。新增决定按编号追加；推翻旧决定时新增一条并注明“替代 D-xxx”，不改写旧条目。

| 编号  | 日期       | 决定                                                                                                                                                                                                                                                                                 | 原因                                                                                                                                                                                                       |
| ----- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-001 | 2026-10-19 | 产品分为 **Web 端**和**设备端（iOS + Android）**，三端共用**同一个后台服务和数据库**。                                                                                                                                                                                               | 需要在电脑上批量整理、在手机上随手记录和接收提醒；一份服务端数据最容易保持多端一致。                                                                                                                       |
| D-002 | 2026-10-19 | **必须登录，在线优先**。数据以服务端为准；手机端缓存最近数据用于离线只读展示，修改需要联网。                                                                                                                                                                                         | 不做本地数据库和同步冲突处理，开发量减少一半以上。                                                                                                                                                         |
| D-003 | 2026-10-19 | **每张业务表都有 `user_id`**，所有查询都按当前登录用户过滤。                                                                                                                                                                                                                         | 数据归属清楚，按用户隔离简单可靠。                                                                                                                                                                         |
| D-004 | 2026-10-19 | 技术栈：TypeScript 全栈。后台用 Node + Hono + Drizzle ORM + PostgreSQL，认证用 Better Auth。                                                                                                                                                                                         | 一种语言贯穿三端，monorepo 内共享类型、校验和业务规则。                                                                                                                                                    |
| D-005 | 2026-10-19 | Web 端单独用 **React + Vite** 实现，与移动端共享业务逻辑和 API 客户端，界面分开写。                                                                                                                                                                                                  | Web 侧重桌面上的批量整理和查看，需要不同于手机的布局。                                                                                                                                                     |
| D-006 | 2026-10-19 | 设备端继续用 **Expo（React Native）**，同时支持 iOS 16+ 和 Android 10+。                                                                                                                                                                                                             | 沿用旧 TD-001 的结论；Android 原生能力已在旧 spike 中验证。                                                                                                                                                |
| D-007 | 2026-10-19 | 先做 **MVP**：登录、重复日常、重要日期、备忘、“今天”、列表和搜索、手机本地提醒。清单、家庭物品等放在下一阶段。                                                                                                                                                                       | 尽快拿到可以每天自己用的版本，再根据使用感受补充。                                                                                                                                                         |
| D-008 | 2026-10-19 | 旧的规划文档、ADR、机器合同和 oracle 工具移入 [`archive/`](../archive/README.md)，不再维护；改用本目录下的几份精简文档和轻量流程。                                                                                                                                                   | 原有流程按多人团队和端侧加密设计，三个月没有产出可用功能。                                                                                                                                                 |
| D-009 | 2026-10-19 | **暂不考虑部署**，先在本地把三端和后台服务完整跑通。                                                                                                                                                                                                                                 | 先验证产品可用，部署地区、备案、监控等问题等需要给别人用时再决定。                                                                                                                                         |
| D-010 | 2026-10-19 | 登录方式为**用户名 + 密码**，不收集邮箱或手机号。认证不再使用 Better Auth，改为服务端自己实现（scrypt 哈希密码、数据库保存会话），**替代 D-004 中“认证用 Better Auth”的部分**。                                                                                                      | Better Auth 以邮箱为核心，用户名登录仍要求邮箱；自己实现只需两张表、逻辑简单，而且所有表都带 `user_id`，不再有例外。代价是忘记密码无法自助找回，见 [数据模型](data-model.md#3-账号)。                      |
| D-011 | 2026-10-19 | iOS 最低版本定为 **16.4**，替代 D-006 中的“iOS 16+”。                                                                                                                                                                                                                                | Expo SDK 57 要求的最低部署版本是 iOS 16.4。                                                                                                                                                                |
| D-012 | 2026-10-20 | **逾期只看日期**：日期早于今天且未处理的实例才算逾期；今天的事即使过了时刻也留在“今天”。同一事项多次逾期合并成一张卡片，显示最近的一次和其余次数。                                                                                                                                   | 产品气质是温和、不催促；按日期判断也让 Web 和手机、不同时区下的结果一致。                                                                                                                                  |
| D-013 | 2026-10-20 | 修改重复规则的**重复方式**（频率、间隔、星期、日期、结束条件）时，服务端把早于今天的开始日期改为今天，新规则从今天生效；只改时刻或标题时不变。每年重复的规则除外，因为它的开始日期就是每年的那一天。                                                                                 | 避免改规则后，过去按新规则本应发生的日子突然变成逾期；已完成和已跳过的历史保留。                                                                                                                           |
| D-014 | 2026-10-20 | 手机通知上的“完成”和“稍后提醒”**会打开应用**再执行；“稍后提醒”固定推迟 10 分钟，只在本机重新排一次通知。                                                                                                                                                                             | 应用被系统关掉时，只有打开应用才能运行代码（调用接口、重新排通知）；后台任务的可靠性因厂商而异，等真实使用后再评估。                                                                                       |
| D-015 | 2026-10-20 | 新建分类或标签时，**重名（不区分大小写）直接返回已有的那个**，不报错。                                                                                                                                                                                                               | 表单里“新建并选中”是最常见的用法，重名时选中已有的即可，用户不需要处理错误。                                                                                                                               |
| D-016 | 2026-10-20 | “仅本次改期”以**原定日期**标识实例：改期只在 `occurrences` 里记一行 `pending` 和新日期，最多前后 60 天；“今天”、逾期和提醒都按实际日期计算。撤销完成或跳过保留改期；“取消改期”才回到原定日期。                                                                                       | 规则展开出来的原定日期是稳定的键，通知 ID、撤销都不受改期影响；不需要为改期另建表。                                                                                                                        |
| D-017 | 2026-10-20 | **低库存只提醒一次**：变成低库存时服务端记下开始时间，`reminders/upcoming` 返回一条立即触发的提醒；第一台排好通知的手机告诉服务端“已提醒”，之后不再返回。恢复到阈值以上再变低，算新的一次。                                                                                          | 不需要服务端推送也能在手机上提醒；多台手机时只有一台会提醒。                                                                                                                                               |
| D-018 | 2026-10-20 | 清单项目的增删改和勾选**不改记录的版本号**，只更新修改时间；清单模板的编辑、分类和标签的管理、批量操作和导出只在 **Web** 上提供，手机端可以从模板新建、另存为模板和删除账号。                                                                                                        | 勾选是最频繁的操作，不应该让另一台设备上正在编辑的标题或截止时间冲突；整理类操作在大屏上更顺手。                                                                                                           |
| D-019 | 2026-10-20 | 回收站里**超过 30 天**的记录由服务端进程在启动时和之后每天自动永久删除。                                                                                                                                                                                                             | 只有一台服务器，不需要单独的定时任务服务；部署后如果有多个实例，再改成数据库层面的定时任务。                                                                                                               |
| D-020 | 2026-10-20 | **iOS 放到后续阶段**，先把 Web 和 Android 做好。代码仍保持 iOS 兼容，只是暂不验证和发布。                                                                                                                                                                                            | 本机还没有 Xcode，日常使用的是 Android 手机；集中精力把两端打磨到可以每天使用。                                                                                                                            |
| D-021 | 2026-10-20 | **直接在 `main` 上开发**，不再走分支和 PR，替代开发计划里原来的“在分支上开发，通过 PR 合并”。                                                                                                                                                                                        | 目前只有一个人开发，PR 只增加步骤；提交前本地跑 `pnpm verify`，推送后由 CI 兜底。                                                                                                                          |
| D-022 | 2026-10-20 | **试用期间服务端放在自己的 Mac 上**，手机和浏览器通过同一 Wi-Fi 访问：`pnpm serve` 长期运行服务端并同时提供 Web 页面；Android 安装独立运行的日常使用版（包名 `dev.lifebook.app`），开发版改为 `dev.lifebook.app.dev`，两者可以同时安装。服务器地址在构建时指定，也可以在应用里修改。 | 不用先决定部署地区就能每天用起来；代价是电脑要开着、出门在外看不到最新数据，提醒不受影响。                                                                                                                 |
| D-023 | 2026-10-20 | 安卓提醒用**精确闹钟**：声明 `USE_EXACT_ALARM`（Android 13 起安装即授予）和 `SCHEDULE_EXACT_ALARM`（Android 12 及以下）。小米等厂商的自启动和省电限制无法由应用绕过，在“我的”里说明设置方法，并提供“测试提醒”让用户自己验证。                                                        | 没有精确闹钟时系统会在省电模式下推迟提醒；Android 14 起 `SCHEDULE_EXACT_ALARM` 默认不授予，要用户手动开。`USE_EXACT_ALARM` 在 Google Play 上只允许闹钟和日历类应用使用，将来上架时需要按审核要求重新评估。 |
| D-025 | 2026-10-20 | **日历**用一个新接口 `GET /api/v1/calendar?from=&to=` 一次取回一段日期内的事项，一次最多 62 天；内容和“今天”一致（周期实例、重要日期、清单截止、备忘提醒），一周从周一开始。过去未处理的实例一律显示为逾期。日历的缓存挂在“今天”下面，完成、跳过或修改记录后一起刷新。               | 月视图最多 6 周（42 天），一次请求就够；和“今天”共用同一套计算，两处看到的状态一致。                                                                                                                       |
| D-024 | 2026-10-20 | **取消注册**：Web 和手机去掉注册页，服务端删除注册接口；账号用服务端脚本 `pnpm create-user <用户名> [显示名称]` 创建，密码在终端里输入。                                                                                                                                             | 只给自己和家人用，不需要开放注册；服务端在局域网里，留着注册接口时同一网络的任何人都能建账号。                                                                                                             |
